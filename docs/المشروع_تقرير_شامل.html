١. نظرة عامة على المشروع

منظومة مستشفى متكاملة قائمة على Flask

نظام iHIS للمعلومات الصحية هو منصة مستشفى شاملة (Hospital Information System) مبنية بلغة Python/Flask، تهدف إلى توحيد جميع عمليات المستشفى في نظام واحد متصل — من الاستقبال والتسجيل، مرورًا بالأقسام السريرية (طبيب، تمريض، مختبر، أشعة، صيدلية، أسنان، علاج طبيعي)، وانتهاءً بالمالية والفوترة والإدارة العليا.

المكوّن التقني الأساسي

واجهة العرض (Backend)

  • Python 3 + Flask (نموذج المصنع create_app())
  • SQLAlchemy + SQLite (للإنتاج يدعم PostgreSQL)
  • Flask-Login للجلسات، Flask-Bcrypt لكلمات المرور
  • Flask-WTF/CSRF لحماية النماذج
  • Flask-Limiter للحد من محاولات الدخول
  • أنظمة Blueprint (22 وحدة) بهيكلية منظمة

واجهة العرض (Frontend)

  • Bootstrap 5.3.3 + نظام تصميم مخصص (Design System v3.0)
  • Chart.js للرسوم البيانية
  • دعم كامل للغة العربية RTL والإنجليزية
  • وضع ليلي (Dark mode)، لوحة أوامر (Ctrl+K)
  • مولد PDF تقارير (ReportLab) بتصميم علامة تجارية

الأدوار (10+1)

  • SuperAdmin — مركز قيادة تنفيذي وإدارة النظام بالكامل
  • Admin — إدارة المنشأة والموظفين والإحصائيات
  • Doctor — الطبيب (EMR، وصفات، طلبات مختبر/أشعة)
  • Nurse — التمريض (علامات حيوية، MAR، خطط رعاية)
  • LabTechnician — فني المختبر
  • Radiologist — أخصائي الأشعة
  • Radiology Technician — فني الأشعة
  • Pharmacist — الصيدلي
  • Physiotherapist — العلاج الطبيعي
  • Dentist — طبيب الأسنان
  • Cashier — المحاسب
  • Receptionist — موظف الاستقبال
  • Patient — المريض (بوابة المريض)

لماذا "نظام تشغيل مستشفى واحد متصل"؟

  • جميع الأقسام تعمل على نفس قاعدة البيانات — لا تكرار للبيانات.
  • خط زمني موحّد (Timeline) لكل مريض يجمع أحداثًا من كل الأقسام.
  • تنبيهات سريرية تلقائية عند النتائج الحرجة.
  • فوترة تلقائية ناتجة عن الأحداث السريرية المكتملة.
  • مهام موجّهة (Tasks) تُنشأ تلقائيًا وتصل للقسم المعني.
  • تحكم كامل في الوصول (Need-to-Know) على مستوى السجل.
مبدأ أساسي جميع لوحات المعلومات (Dashboards) تعرض بيانات من استعلامات حقيقية مباشرة من قاعدة البيانات — لا توجد أي أرقام مزيّفة أو "محتوى تجريبي وهمي".

٢. مميزات المنصة

قائمة شاملة بقدرات النظام مصنّفة حسب القسم

يمكن الوصول إلى "مركز اكتشاف القدرات" الكامل داخل التطبيق عبر /super-admin/capabilities، ويعرض أكثر من 60 ميزة حقيقية في 10 مجموعات:

السريرية (Clinical)

  • سجل طبي إلكتروني (EMR) بدورة حياة كاملة (مسودة ← توقيع ← قفل) مع سلسلة تعديلات مرقّمة
  • التشخيصات مع أكواد ICD-10 وتمييز التشخيص الأساسي
  • الوصفات الطبية مع فحص تلقائي للحساسية والتفاعلات الدوائية
  • قائمة المشكلات (Problem List) والحساسيات المنظمة
  • اللقاحات مع تتبع موعد الجرعة التالية
  • المتابعات والتذكيرات الوقائية (Preventive Sweep)
  • نظرة المريض 360 (Patient 360) بخط زمني موحّد

التشخيص (Diagnostics)

  • المختبر: دورة حياة كاملة (طلب ← قبول ← جمع ← معالجة ← نتيجة ← تحقق ← نهائي)
  • اكتشاف تلقائي للنتائج غير الطبيعية والحرجة SQL
  • الأشعة: جدولة وتنفيذ وتقارير (مسودة ← توقيع ← قفل)
  • تقرير أشعة مع سجل إصدارات للترقيعات

الدواء (Medication)

  • مخزون الصيدلية (FEFO) مع اشعارات انخفاض/انتهاء الصلاحية
  • صرف الأدوية بذريعة شرطية آمنة ضد التزامن (Atomic decrement)
  • كاشف التفاعلات الدوائية (Drug Interaction)
  • مراجعة دوائية (Med Reconcile) مع كشف التناقضات
  • تدخلات الصيدلي إلى الطبيب (Interventions) بسجل محادثة
  • سجل حركة المخزون (StockTransaction) بالكامل

التمريض (Nursing)

  • تسجيل العلامات الحيوية مع إنذارات الحالات غير الطبيعية
  • سجل الصرف الدوائي (MAR) مع نتائج الجرعات
  • نسبة الإدخال/الإخراج (Intake/Output)
  • خطط الرعاية وملاحظات التمريض لكل وردية
  • تقييمات مخاطر التمريض (سقوط، قرح فراش)

العلاج الطبيعي (Rehab) وطب الأسنان

  • العلاج الطبيعي: تقييمات، خطط، جلسات، تتبع تقدم، مكتبة تمارين
  • طب الأسنان: سجل أسنان، مخطط أسنان (Dental Chart)، خطط علاج، حالات تقويم

العمليات والمالية

  • الاستقبال: حجز مواعيد مع كشف تعارض، طابور انتظار، تسجيل مرضى
  • قبول/تنويم/خروج (Admissions) مع إدارة الأسرة والأجنحة
  • الفوترة: فواتير، دفعات، كتالوج خدمات، توليد فواتير تلقائي
  • الإحالات وفريق الرعاية والحالات متعددة التخصصات (MDT)

الذكاء الاصطناعي (AI) — 15 خدمة

  • تشخيص تفريقي، تفسير مختبر، التنبؤ بالمخاطر، كتابة كود ICD-10
  • ملاحظات SOAP، مجموعات أوامر ذكية، تواصل مع المريض (عربي/إنجليزي)
  • مراجعة دوائية لصيدلي سريري، التنبيهات السريرية
  • كشف الكسور (YOLOv8)، تجزئة الأسنان (U-Net)
  • ذكاء رعاية صحية للاستفادة والاستشارة التلقائية
لوحة القيادة التنفيذية يملك SuperAdmin "مركز القيادة" (Command Center) الذي يعرض ~40 مؤشر أداء حقيقي عبر كل الأقسام، بالإضافة إلى قدرة معاينة أدوار الآخرين لاستكشاف الواجهات.

٤. نظام الأذونات والتحكم في الوصول

أمان دقيق على المستويين: صلاحية ومستوى السجل

نظام الصلاحيات (RBAC) — app/permissions.py

تتبع الصلاحيات نمط تسمية <المورد>_<الإجراء> (مثل MEDICAL_RECORD_SIGN, LAB_RESULT_VERIFY, PRESCRIPTION_DISPENSE)، مع أكثر من 80 صلاحية مرتّبة حسب المورد. كل دور (Role) مرتبط بمجموعة صلاحيات محدّدة عبر جدول وسيط.

مثال — صلاحيات الطبيب

  • عرض المريض + دورة حياة السجل الطبي كاملة
  • طلبات المختبر والأشعة + عرض النتائج
  • إنشاء/تعديل/إلغاء الوصفات
  • AI استخدام الذكاء الاصطناعي (تشخيص، مخاطر، مراجعة دوائية)
  • التنبيهات والبحث والحساسيات والمشكلات

مثال — صلاحيات الصيدلي

  • عرض المريض + صرف الوصفات
  • إدارة المخزون الكامل
  • AI مراجعة دوائية + تفاعلات الأدوية
  • إنشاء/إكمال المراجعة الدوائية + التدخلات
  • عرض نتائج المختبر والتسجيل الزمني

التحكم في الوصول على مستوى السجل (Need-to-Know)

كوّن ملف app/access.py سياسة "الحاجة للمعرفة". لا يستطيع أي موظف الوصول لسجل مريض إلا إذا كانت لديه علاقة موثّقة:

  • المريض — يصل فقط لسجله الخاص.
  • Admin / SuperAdmin — وصول إشرافي لكل المرضى.
  • الطبيب — من كتب سجلًا/تشخيصًا/وصفة/طلبًا/موعدًا/حوّله.
  • الممرض — من سجّل علامة حيوية/ملاحظة/خطة رعاية.
  • طبيب الأسنان/العلاج الطبيعي — عبر السجلات الخاصة بهم.
  • أخصائي الأشعة — من وقّع تقريرًا للمريض.
  • فني المختبر — من أنشأ/تحقق من نتيجة.
  • الصيدلي — إذا وجدت وصفة للمريض.

يتم فرض ذلك عبر الديكور @patient_access_required ودالة require_patient_access()، ووظيفة accessible_patient_ids() لترشيح القوائم.

سلسلة الحماية الإضافية

  • CSRF على كل نموذج.
  • Rate limiting للدخول (10/دقيقة) والتسجيل (5/ساعة).
  • حماية open-redirect في معامل ?next=.
  • حجب الملفات الخاصة (يرفع الطريق /static/uploads/ و /static/ai_models/ يمنع 404) — حماية PHI.
  • فحص صارم للرفع (magic bytes بدل الاعتماد على الامتداد).
  • تجميد حالة الطلب من الخادم (لا يسمح للعميل بفرض حالة).
  • تسجيل تدقيق (AuditLog) لكل تعديل مع IP وبيانات المتصفح.
  • تفرد فوترة (قيود Idempotency) لمنع تكرار الدفعات.

٥. وحدات النظام التفصيلية

كيف تعمل كل وحدة وتتفاعل مع غيرها

النظام مقسّم إلى 22 Blueprint (وحدة)، ولكل منها بادئة URL مستقلة. إليك شرح لكل وحدة وكيف تعمل:

الاستقبال (Reception) — /reception

نقطة دخول المريض: حجز المواعيد (مع كشف تعارض has_appointment_conflict)، فحص الدخول (Check-in)، الطابور، وتسجيل مرضى جدد. عند إكمال زيارة يتم توليد فاتورة استشارة تلقائيًا.

الطبيب (Doctor) — /doctor

مركز العمل الطبي: نظرة 360 للمريض، إدخال/تعديل السجلات الطبية مع توقيع إلكتروني وقفل، كتابة الوصفات مع فحص تلقائي للحساسية والتفاعلات (flag_prescription_safety) وإنشاء تنبيهات، طلبات المختبر والأشعة (تنشئ مهام + إشعارات)، والإحالات. عند إكمال الموعد تُنشأ فاتورة الاستشارة.

المختبر (Lab) — /lab

دورة حياة صارمة: طلب ← قبول ← جمع ← استلام ← معالجة ← إدخال نتيجة ← تحقق ← نهائي. تطبيق آلي للكشف عن الشذوذ (apply_lab_abnormality)، مع دعم تعديل نتيجة محققة (يتطلب سببًا ويعيد الفتح). عند النتيجة الحرجة: إشعار فوري لفئة الأطباء + تنبيه CRITICAL_LAB. التحقق يولّد فاتورة المختبر.

الأشعة (Radiology) — /radiology

جدولة/تنفيذ الطلب وتحميل الصور وإنشاء التقارير (توقيع وقفل وسجل إصدارات). تم دمج وحدة سلامة الأشعة الكاملة (انظر القسم ٩): فحص سلامة CT/MRI، ملف سلامة المريض، رصد الجرعات، مستويات مرجعية، نتائج حرجة. عند التوقيع تُنشأ فاتورة الأشعة ويُبلَّغ الطبيب المطلوب والمريض.

الصيدلية (Pharmacy) — /pharmacy

إدارة المخزون (FEFO: أول انتهاء صلاحية يُصرف أولًا) بعدّ تناقص ذري آمن، صرف الوصفات مع تسجيل سجلّ حركة كامل، كشف التفاعلات (DrugInteraction)، المراجعة الدوائية ضد قائمة الأدوية المنزلية مع توليد التناقضات، تدخلات الصيدلي إلى الطبيب، ومحطة عمل الصيدلاني السريري بالذكاء الاصطناعي.

التمريض (Nursing) — /nursing

تسجيل العلامات الحيوية (مع إنذار تلقائي للحالات غير الطبيعية والحرجة)، نسبة الإدخال/الإخراج، خطط الرعاية، وسجل الصرف الدوائي MAR الذي يتيح تسجيل نتيجة كل جرعة (Administered/Refused/Held/Missed) مع إشعار الطبيب في الحالات الحرجة.

طب الأسنان والعلاج الطبيعي

Dentistry (/dentistry): سجل أسنان، مخطط أسنان لكل سن حسب FDI، خطط وإجراءات، صور، حالات تقويم. Physiotherapy (/physiotherapy): تقييمات وظيفية، خطط، جلسات، تتبع تقدم، مكتبة تمارين، ونتائج وظيفية (FIM/Barthel/TUG).

الفوترة والقبول (Billing / Admissions)

Billing: فواتير بأتوازن، دفعات بقيود Idempotency، كتالوج خدمات. Admissions: إدارة الأجنحة والأسرة، تنويم وخروج، مع توليد فاتورة الغرفة عند الخروج تلقائيًا.

التنسيق السريري (Care) والمهام (Tasks)

Care: إحالات بدرجة إلحاح، فريق رعاية، حالات متعددة التخصصات. Tasks: محرك مهام عام ينقل المهام بين الأقسام مع سجل نشاط TaskActivity — تنشأ المهام تلقائيًا عند الطلبات السريرية.

البحث والخط الزمني والتنبيهات

Search (/search): بحث عام (Ctrl+K) وعي الحساسية للصلاحيات والوصول. Timeline: خط زمني موحّد لكل مريض يجمع أحداث كل الأقسام. Alerts (/clinical): محرك تنبيهات بدورة حياة (مفتوح ← مُقَرّ ← محلول) بدرجات خطورة.

بوابة المريض (Patient)

لوحة مريض تعرض المواعيد، النتائج، الوصفات، المستندات (رفع/تحميل)، الفواتير، الرسائل للطبيب، تاريخي الطبي، وحتى قسم "أشعتي" (My Radiology) لاستعراض ملف السلامة والجرعات الإشعاعية بُلغة مبسطة.

الإدارة (Admin) والإدارة العليا (SuperAdmin)

Admin: لوحة إيرادات حقيقية، إدارة الموظفين والأقسام والأطباء، إحصائيات، تحسين مواعيد، ومساعد ترميز. SuperAdmin: مركز قيادة تنفيذي (~40 مؤشر)، إدارة المستخدمين/الأدوار/الصلاحيات/التدقيق/الإعدادات/النسخ الاحتياطي، فحص الوقاية، ومعاينة أدوار الآخرين.

٧. آلية عمل Gemini LLM بالتفصيل

من الطلب حتى التوصية النهائية

خط سير العمل (Pipeline)

  1. التحقق من التوفر — تتحقق gemini_available() من وجود GEMINI_API_KEY.
  2. جمع السياق — يجمع _collect_patient_context() الأدوية النشطة، آخر التحاليل، العلامات الحيوية، والتشخيصات، ويصيغها نصيًا.
  3. بناء الـ Prompt — تدمج الخدمة نظام prompt (System Prompt) مع سياق المريض + تنسيق الإخراج المطلوب (JSON).
  4. استدعاء الـ API — تُرسل عبر HTTP إلى generativelanguage.googleapis.com بدرجة حرارة محددة لكل ميزة.
  5. تحليل JSON — _call_gemini_json() تزيل فواصل markdown وتوزّع JSON.
  6. دمج الحقائق الحتمية — مثل علامة الشذوذ للمختبر تُحسب دائمًا محليًا ولا تُترك للـ LLM.
  7. التسجيل والتدقيق — تسجل _log_call() في سجل النشاط وتخزَّن في AIRecommendation.

نظام Prompt (System Prompt)

لكل خدمة شخصية محددة بوضوح وتوجيهات سريرية، مثل: "أنت طبيب معتمد متخصص في التشخيص" أو "أنت مبرمِز طبي خبير في ICD-10-CM" أو "أنت أخصائي تثقيف مريض". جميع الـ Prompts تؤكد: دعم القرار فقط، ولا تُغني عن حكم الطبيب، وتذكر أن الذكاء الاصطناعي لا يحل محل الاستشارة.

تنسيق الإخراج القياسي (مثال: التشخيص التفريقي)

يُطلب من النموذج إرجاع JSON بهذا الهيكل العام:

  • differentials — قائمة مرتبة (rank, diagnosis, icd10, confidence, reasoning, next_steps, urgency)
  • clinical_reasoning — الاستدلال السريري
  • red_flags — العلامات التحذيرية
  • disclaimer — تنويه

الاحتياط (Fallback) — متعدد الطبقات

الطبقةالوصف
1. البيانات الحتميةتُحسب دائمًا محليًا (شذوذ، عتبات، درجات أساسية)
2. قواعد eristicsعند غياب المفتاح أو فشل الاستدعاء — قواميس/درجات مكتوبة يدويًا
3. إخراج منظمعند خطأ JSON يُرجع النص الخام كنص قابل للعرض
4. خطأ نظيف{'available': False, 'error': ...} بدون أي 500
خصوصية البيانات تُطبّق "تقليل البيانات" (Data Minimization): لا يُرسل اسم المريض الكامل أو رقم MRN إلى Gemini، بل فقط البيانات اللازمة سريريًا (العمر، الجنس، الأدوية، الحساسيات، التشخيصات، التحاليل).

٨. نماذج الرؤية الحاسوبية (صور)

كشف الكسور وتجزئة الأسنان

YOLOv8 كاشف الكسور

ملف app/services/ai/fracture_detection.py + نموذج best.pt (مضبوط بدقة، YOLOv8-nano). يكتشف أصنافًا: كسر، يد، مثبتات معدنية، فخذ، ساق، كتف.

  • detect_fracture(upload_file) — يرفع الصورة ويرجع النتائج: هل يوجد كسر؟، اكتشافات (تسمية + ثقة + نسبة)، توزيع الأصناف.
  • يحفظ الصورة الأصلية ونسخة موسومة بنتائج الكشف.
  • يحمّل النموذج بشكل كسول وخيط آمن (lazy singleton).

النهاية: /ai/fracture-detection — متاح لأطباء الأشعة والأطباء والممرضين والعلاج الطبيعي وطب الأسنان والإدارة.

U-Net تجزئة الأسنان

ملف app/services/ai/tooth_segmentation.py + نموذج best_unet.keras (قالب RGB 256×256، دقة Dice 84.76% / IoU 73.56%).

  • segment_tooth(upload_file) — يقسّم صورة الأسنان وينتج قناع (Mask) فاصلًا مع نسبة التغطية.
  • يدعم تنسيقين للنموذج (RGB أو رمادي+CLAHE) ويختار المعالجة تلقائيًا حسب شكل المدخل.
  • تخزين خاص داخل var/uploads/ai/tooth/.

النهاية: /ai/tooth-segmentation — متاح لأطباء الأسنان والأشعة والممرضين والإدارة.

خصوصية الصور الطبية

  • جميع الصور المرفوعة تُحفظ في مجلد خاص (var/uploads/) وليس في المجلد العام.
  • الطريق العام /static/ai_models/ و /static/uploads/ محجوب (يعيد 404) لحماية بيانات المرضى.
  • تصل إلى الصور عبر نقطة /ai/media/... الخاصة المقيّدة بالأدوار، مع حماية ضد path traversal.
  • فحص نوع الملف والسماح فقط بالصيغ الآمنة (png/jpg/jpeg).
سلوك Graceful إذا لم يكن النموذج مثبتًا على الخادم، تُرجع الدالة رسالة واضحة ("النموذج غير مثبت") بدلًا من التعطل — تم التحقق منه بالاختبارات.

٩. وحدة سلامة الأشعة والجرعة الإشعاعية

سلامة المريض أثناء التصوير الطبي
مبادئ السلامة غير القابلة للتفاوض ① MRI لا يستخدم إشعاعًا مؤينًا — النظام يميّز بوضوح بين ما يشعّ وما لا يشعّ. ② سجلات الجرعة لا تُزيّف أبدًا. ③ العتبات المرجعية المؤسسية ليست حدود جرعة مطلقة للمريض. ④ الذكاء الاصطناعي لا يرفض التصوير تلقائيًا أبدًا.

خدمتا السلامة (في app/services/radiology/)

خدمة السلامة

RadiologySafetyService — تقييم سلامة CT/MRI/التباين. ترجع دائمًا {safety_status, warnings, profile}.

  • CT: تفاعل تباين سابق، وظائف الكلى (eGFR)، الحمل، الحساسية.
  • MRI: حالة الفحص، مصنف أمان الغرسات (MR Unsafe/Conditional/Unknown)، تباين الجادولينيوم.
  • الفحص الآمن للتباين حسب النوع.

خدمة الجرعة

RadiationDoseService — حساب جرعات الإشعاع.

  • ملخص سنوي/تراكمي حسب الطريقة ومنطقة الجسم.
  • تمييز الجرعة المقاسة عن المقدّرة (بتقديرات ICRP-103/AAPM مرجعية).
  • مقارنة مع المستويات المرجعية + تنبيهات الجرعة.
  • تصحيح السجل مع الاحتفاظ بالأصل.

  • ImagingPreparationProtocol — بروتوكولات التحضير (قابلة للإعداد)
